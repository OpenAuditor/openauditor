# LLM09: Misinformation

**LLM09:2025 · Rank #9 in the OWASP Top 10 for LLM Applications 2025 (expanded from "Overreliance") · Severity: Medium to High, depending on what users do with the answers**

Models produce false or misleading output that sounds authoritative, and people or systems act on it. The 2025 edition treats this as two linked problems: the model being wrong (hallucination, outdated knowledge, bias) and the product or team trusting it without checks (overreliance).

---

## 30-Second Summary

For builders, misinformation shows up in two places:

1. **In your product:** your AI feature tells a customer something false about your prices, policies, their account, the law or their health, and they act on it. You are responsible for what your bot says.
2. **In your engineering:** your coding assistant writes insecure or outdated code, invents packages, or reviews code and calls it safe, and you ship it.

**Real case:** In *Moffatt v. Air Canada* (February 2024), Air Canada's website chatbot told a grieving customer he could claim a bereavement fare refund after travelling. That wasn't the airline's policy. Air Canada argued the chatbot was responsible for its own words; the British Columbia Civil Resolution Tribunal rejected that and ordered the airline to pay. Courts and regulators treat your chatbot's statements as your statements.

## In Your Product

### Ground answers in your own data, and show the source

```typescript
// VULNERABLE: the model answers policy questions from its general knowledge
const reply = await ai.chat({ system: 'You are a helpful support agent.', messages });

// SAFER: answer only from retrieved, approved policy text, cite it, and admit gaps
const docs = await searchApprovedPolicies(question);   // official, current content only
const reply = await ai.chat({
  system: `Answer using ONLY the policy excerpts provided. Quote the relevant
sentence and include its title. If the excerpts don't answer the question,
say you don't know and offer to connect the customer with a person.`,
  messages: [...messages, { role: 'user', content: formatWithSources(question, docs) }],
});
```

### Don't let the model make commitments

Prices, refunds, eligibility, delivery dates and anything contractual should come from your systems through tools, not be generated. If the model needs to state a price, it calls `getPrice()` and repeats the result.

### Design the UI for fallibility

- Label AI answers as AI-generated and show the sources they used
- Make "talk to a human" easy, and route high-stakes topics (refunds, legal, medical, financial, safety) to people or fixed content
- Let users report wrong answers, and review those reports

### Measure it

Keep an evaluation set of real questions with correct answers (especially the ones that went wrong in production) and run it on every prompt, model or data change. Track the rate of unsupported claims, not just user satisfaction.

## In Your Engineering

### 1. Generated Code Shipped Without Review

```javascript
// A developer asks an AI coding assistant to:
// "Write a function to check if a user is an admin"

// LLM generates:
function isAdmin(user) {
  return user.role === 'admin'; // Simple check
}

// Looks reasonable. Developer ships it.
// Missing:
// - Server-side verification (what if user.role comes from client-controlled JWT payload?)
// - Privilege escalation checks
// - The check should be on the server, not in client-side code

// The "correct" check is far more involved, but the LLM produced a simple, 
// plausible-looking answer that passes a superficial code review.
```

**Mitigation:** Every security-relevant function generated by AI must go through explicit security review. Mark them:

```typescript
// AI-GENERATED: Verify this logic independently before merging
// Security-relevant: admin access check
async function isAdmin(userId: string): Promise<boolean> {
  // Fetch from database: don't trust client-provided role claims
  const user = await db.users.findById(userId);
  return user?.role === 'admin';
}
```

### 2. Security Assessments Done Only by AI

```python
# VULNERABLE workflow: 
# Developer asks AI: "Review this code for security vulnerabilities"
# AI says: "Looks secure to me!"
# Developer ships it.

# The AI may have missed:
# - Business logic flaws that require understanding the full system
# - Authentication issues that depend on how the function is called
# - Race conditions visible only at runtime
# - IDOR issues that require understanding the data model

# SECURE workflow:
# AI review is INPUT to a human security review, not a replacement
# Use the [Test Auth Flows prompt](../../10-security-testing/prompts/test-auth-flows.md)
# Run SAST (Semgrep): automated, deterministic
# Run the manual testing checklist: human judgment
# Perform threat modelling: architecture-level review
```

### 3. Hallucinated CVEs, Packages and Security Advice

Models invent CVE IDs, package names, config options and API methods, and their knowledge stops at a training cutoff. Invented package names are actively exploited: see [LLM03: Supply Chain](./LLM03-supply-chain.md#2-packages-your-ai-assistant-invented). Outdated advice is just as common; see [Deprecation and Version Hygiene](../../00-foundations/deprecation-and-version-hygiene.md).

```python
# Asked "Is package X affected by CVE-XXXX-NNNNN?", a model may confidently
# answer "Yes, upgrade to version Y" for a CVE or a version that doesn't exist.

# NEVER rely on LLM for CVE information
# Always verify at:
# - nvd.nist.gov
# - github.com/advisories
# - The package's official security advisory

# SECURE: Use LLMs to help you interpret CVEs: not as the source
# "I found CVE-XXXX-NNNNN in the NVD. Here's the description. 
#  Help me understand if our usage pattern is affected."
```

## Building Appropriate Human Oversight

### 1. Mandatory Review Gates for AI-Generated Code

```markdown
<!-- .github/pull_request_template.md: add a security section -->
## Security checklist (for AI-assisted code)

If this PR includes AI-generated code, confirm:
- [ ] I have read and understood every line of AI-generated code
- [ ] Security-relevant logic (auth, data access, input handling) reviewed by a second developer
- [ ] Generated code run through `npm audit` / `semgrep` before merging
- [ ] No AI-generated credentials, API keys, or secrets included
- [ ] Business logic verified against requirements, not just "looks right"
```

### 2. Confidence Indicators in AI Outputs

A model's stated confidence is not well calibrated, so don't treat "[HIGH CONFIDENCE]" as evidence. What this pattern is good for is forcing a verification step on security-critical topics regardless of what the model says.

```python
# Flag security-critical answers for verification
SYSTEM_PROMPT = """You are a security assistant. When answering:
- Always indicate your confidence level: [HIGH CONFIDENCE] / [MEDIUM CONFIDENCE] / [VERIFY INDEPENDENTLY]
- For security-critical information (CVEs, compliance requirements, legal matters): always add [VERIFY INDEPENDENTLY]
- For code snippets with security implications: always note specific things to check
- Never present information as certain when you're not sure"""

# Then filter for verification flags:
def process_security_response(response: str) -> dict:
    requires_verification = '[VERIFY INDEPENDENTLY]' in response
    is_security_critical = any(term in response.lower() for term in [
        'cve', 'vulnerability', 'gdpr', 'pci', 'hipaa', 'authentication',
        'password', 'encryption', 'compliance'
    ])
    
    return {
        'content': response,
        'requires_human_verification': requires_verification or is_security_critical,
        'confidence': 'low' if '[VERIFY INDEPENDENTLY]' in response else 'medium',
    }
```

### 3. Automated Verification Where Possible

```javascript
// Don't just ask the AI if code is secure: run actual checks
const securityChecks = [
  { name: 'SAST (Semgrep)', command: 'semgrep --config p/security-audit .' },
  { name: 'Dependency audit', command: 'npm audit --audit-level=high' },
  { name: 'Type check', command: 'npx tsc --noEmit' },
  { name: 'Tests', command: 'npm test' },
];

// These checks run before any AI-generated code can be merged
// They catch what the AI missed, and they always catch something
```

## Audit Checklist

- [ ] Customer-facing answers are grounded in approved, current content and show their sources
- [ ] Prices, refunds, eligibility and other commitments come from tools or fixed content, never generated
- [ ] High-stakes topics route to a human or fixed content; "talk to a person" is easy to reach
- [ ] AI answers are labelled, and users can report wrong ones
- [ ] An evaluation set of real questions runs on every prompt, model or data change
- [ ] AI-generated security-relevant code requires explicit human review before merging
- [ ] PR template includes AI code checklist
- [ ] CVE information always verified at NVD/GitHub advisories: never taken from LLM output
- [ ] Compliance requirements (GDPR, PCI, HIPAA) verified with legal counsel, not LLMs
- [ ] SAST and dependency scanning runs automatically: don't rely on AI code review alone
- [ ] Critical business decisions requiring AI input have a human approval step
- [ ] AI-generated policies, contracts, or legal text reviewed by qualified humans
